spec을 검토하여 불명확하거나 잘못된 부분을 이의제기한다.

- `$ARGUMENTS`가 있으면 해당 파일만 대상. 다음 형식 모두 허용:
  - `plan` → `plan.md`
  - `spec-001` → `specs/spec-001.md`
  - `spec-001-002` → `specs/spec-001-002.md` (서브스펙)
  - `001` → `specs/spec-001.md`
  - `001-002` → `specs/spec-001-002.md`
  - `1` → `specs/spec-001.md`
- `$ARGUMENTS`가 없으면 현재 진행 중인 spec 대상
- 아래 관점에서 검토하여 문제가 있는 항목만 질문/이의제기:
  1. **모호함** — 구현자가 다르게 해석할 수 있는 표현
  2. **누락** — 동작하려면 반드시 필요한데 명시되지 않은 조건/케이스/예외
  3. **충돌** — spec 내부 또는 CLAUDE.md·plan.md와 상충하는 내용
  4. **과잉** — 범위 밖이거나 불필요하게 복잡한 요구사항
- 항목마다 **어디가 문제인지** + **왜 문제인지** + **어떻게 바꾸면 좋은지(제안)** 를 간결하게 제시
- 칭찬이나 긍정적 평가는 생략 — 문제 있는 부분만 다룬다
- 코드는 작성하지 않는다
- 검토 중 정의가 불분명한 도메인 용어를 발견하면 `plan.md`의 `## 용어 정의` 섹션에 추가한다. 섹션이 없으면 새로 만든다. 유저에게 정의를 물어보고 확정 후 추가할 것
